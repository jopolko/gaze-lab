2026-11-18: built web/spike (three.js WebGL2: one-plane moire ground shader, instanced wireframe pylons/rings, half-res tracer feedback + colour split, mouse/?cam eye steering). User ran it on the laptop (Intel UHD 620): 59.9 fps, "already looks great". Godot build on the same machine: 23-35 fps, CPU-bound with the tracker, GPU-bound without.

**Why:** the Godot web export (40 MB single-threaded wasm, shader warm-up 4-12 s, second world render for tracers) is the cost; the game needs a road, gaze L/M/R control and a few psychedelic shaders. User wants ridiculous frame rate, minimal/line-drawing look, maybe a watch eventually (watch has no front camera, so phones first).

**How to apply:** build forward in web/spike (served by `python web/spike/serve.py`, port 8072; --lan 8472). Reuse web/stargaze tracker.js (MediaPipe, vendored three). Keep Godot version as reference, don't port features wholesale. web/ is untracked on purpose (repo is public; music licences). Consider OffscreenCanvas worker rendering to free the main thread for the tracker. See [[project-downhill-vision]], [[feedback-never-scroll-menus]].

2026-11-18 late night, KEY INSIGHT: Godot needed no calibration because its control was a forgiving LOCK-ON (RunRig.gd ~line 1809), not lane=zone. Each candidate keeps a leaky "want" (fills while the eyes are in its zone, middle at 0.35 pace; drains 3.0/s when eyes are on a side else 0.6/s); first lock after 0.11*qk s; once locked it holds however the eyes wander, committed for 0.5*qk s, a change of mind needs 0.35*qk s then 0.14*qk s; no change in the last 0.25 s before reaching; board auto-steers to the locked thing; choices are real objects far apart. KitEye zones only need to be right on average over ~0.1-0.35 s. Spike versions: web/spike (Godot's own tracker JS dumped from GazeCamJS.source() + KitEye zones, lane=zone, thresholds lowered 0.35/0.2) and web/spike-light (STARGAZE tracker in worker + KitEye zones + both-ways side learning + the LOCK-ON; served at http://localhost:8072/spike-light/). Godot's own tracker ran ~100-110 ms/frame (limbus fit + geometry extras the zones don't use) vs ~40-50 ms for the light tracker; Godot defaults laptops to CPU model and times the other chip.

**Correction 2026-11-18 (late): Godot is 3-LANE / 3-ZONE, not "choice of two".** RunRig._gen_feats comment says "choice of two" but the code builds four layouts: pair 22% (thing each side, middle open / rock slalom / boosts), centre 22% (one good thing in the middle, rocks both sides), triple 36% (three different things L/M/R), flank 20%. Selection (RunRig._trail_pick) is relative stepping from the locked thing: look left = the thing left of it, right = right of it, middle = keeps the lock (with nothing locked: the thing in the board's own lane); nothing further that way = no change. downhill-three now does this (patch_3lane); the two-choice rewrite was a mistake from trusting a comment. Test harness note: synthetic frame times run ahead of real time, so afterwards the real loop sees negative dt (clamped now).

**2026-11-18 night: eye control findings (downhill-three, commit "eye model").** (1) Glasses distort one eye: in the user's logs eye A moved +0.014 left / -0.052 right, eye B +0.037 / -0.042, so averaging gave a left/right lopsided signal; WITHOUT glasses control was "much better, almost playable, ~3 missed targets in 85 s" (zone L118/R86, board middle 66%). (2) The fix that worked was `web/downhill-three/eyemodel.js`: a 3-state filter (L/M/R) over BOTH eyes, per-eye offsets per side, middle floats with all readings weighted by posterior, offsets saved in localStorage `spike_em`; old threshold detector via `?nomodel`. Simulation (on eyes like the logs) 77% vs 68%, big win only under drift (middle recall 39% -> 63%). (3) Godot is 3-lane/3-zone; Godot's lock is released after each thing and its board follows the eyes continuously; copying only "middle keeps the lock" parked the board left. Current rule: lane follows the eyes, held until the thing is passed, free again at each pass. (4) Head features (yaw/pitch/roll/face pos/size/lids) overfit; only eye A follows yaw (CV R2 ~0.4), already absorbed by the floating middle: no head compensation. (5) Edge looks give hx ~ +/-0.045 but in-game targets are only ~0.01 away from centre, so side look-target cards were added. Still to test: the model WITH glasses; lane changes are ~8/10 s (a bit twitchy). Logs: web/spike/logs, analysis scripts in web/downhill-three (analyze_drift.py).
